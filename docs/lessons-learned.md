### 2026-09-03: 状態値のリネーム移行は「旧状態が何を証明していたか」で移行先を決める／共有一覧APIに他人の非公開フィールドを載せない

- **種別**: Codexレビューで採用（Phase 7-5 割り勘精算フロー改訂、PR #111）
- **対象領域・関連ファイル**: `backend-workers/drizzle/0009_settlement_accounts.sql`、`backend-workers/src/routes/expense-splits.ts`
- **何が起きたか / 対応**:
  1. 割り勘の承認者を「負担者」から「立替者（受領側）」へ入れ替えるにあたり、status `approval_requested` を
     `payment_reported`（負担者が支払報告済み）へリネームした。既存行を単純に名前対応で
     `approval_requested → payment_reported` に移行しようとしたが、旧 `approval_requested` は
     「立替者が受領申請を出しただけ」で、負担者が実際に支払った証拠ではない。そのまま移行すると
     立替者が負担者の操作なしに精算確定（＝家計簿レコード生成）できてしまう。→ 旧行は
     `requested`（負担者の `mark-paid` を改めて要求する状態）へ移行した。
  2. `GET /api/expense-splits` は「自分が立替者 or 負担者」の内訳を1つの一覧で返す共有エンドポイント。
     負担者が選んだ支払い元口座ID（`debtor_account_id`）をレスポンスに常時含めていたため、立替者にも
     相手の口座IDが見えてしまっていた。→ `role === 'debtor'` のときだけ返すようにした。
- **次回の行動規則**:
  - **状態値をリネーム／意味変更するマイグレーションでは、名前の対応ではなく「その旧状態のとき、誰が何をした
    ことが確定しているか」を基準に移行先を決める**。判断に迷う中間状態は、より手前の（＝関係者の操作を
    改めて要求する）状態に倒す。
  - **複数ロールが同じ行を1つの一覧で受け取るエンドポイントでは、ロール別に見せてよいフィールドを分ける**。
    他ユーザー個人の口座ID・設定値などの識別子を、関係者だからといって無条件に返さない
    （既存の「他人のリソースは404」＝common-notes.md 10章 と同じ、情報最小化の原則）。
- **状態**: 有効
- **根拠**: Phase 7-5 改訂のCodexレビュー（PR #111 の P1/P2）。いずれも検証のうえ採用・修正済み。

### 2026-09-02: D1（行ロック無し）での多レコード書き込み・状態遷移の競合対策と、フロント側の入力チェック整合

- **種別**: Codexレビューで採用（Phase 7-5 割り勘・精算管理 F-04、PR #106 / #108 / #109）
- **対象領域・関連ファイル**: `backend-workers/src/routes/expense-splits.ts`、`expenses.ts`、`src/lib/split-calc.ts`、`frontend/src/components/kakeibo/SplitFields.tsx`
- **何が起きたか / 対応**:
  1. 親レコード（expenses）＋子レコード（expense_splits）＋残高UPDATEを別々の `DB.batch()` に分けていたところ、「支出と残高は確定したが内訳の書き込みに失敗」→再送で二重計上、の指摘。→ **1つの `DB.batch()` にまとめて原子化**。子INSERTの親IDは同一トランザクション内の `(SELECT MAX(id) FROM expenses)` で解決（batchはSQLiteトランザクションで隔離され途中に他INSERTが割り込まない）。ID採番が不要な付随マスタ（external_persons＝名前だけの行、参照整合性に影響しない）だけは先行batchで作ってよい。
  2. 状態遷移を「SELECTで現status確認 → IDのみ指定でUPDATE」で実装していたところ、並行する2つの正当な遷移が両方通って状態機械を破る指摘（例: approval_requested から approve と hold が同時通過）。→ **遷移元statusをUPDATEのWHERE句にも含め、`meta.changes === 0` なら400を返す**。
  3. フロントの入力チェックがバックエンドのスキーマ制約を一部取りこぼしていた指摘（金額の小数、個別割合>100、`/households/me` に自分が含まれ割り勘の相手に自分を選べる等）。→ **フロント側チェックはバックエンドのZodスキーマと1対1で揃える**。ログイン中ユーザーIDが必要な場面はアクセストークン（JWT）の `sub` から取得（`tokenStorage.getCurrentUserId()`）。
- **次回の行動規則**:
  - D1で「関連する複数の書き込み」は必ず単一 `DB.batch()`。分ける場合は「失敗しても参照整合性・金額に影響しない付随データか」を必ず自問する。
  - D1で check-then-update をやるときは、必ず判定条件をUPDATEのWHERE句にも入れ、更新行数で成否を判定する（行ロックが無いため事前SELECTだけでは競合を防げない）。
  - APIの入力バリデーションを追加・変更したら、対応するフロントのクライアント側チェックも同じ制約で更新する（数値の整数・上下限、識別子の重複・自己指定など）。
- **状態**: 有効
- **根拠**: Phase 7-5 のCodexレビュー（PR #106 P1/P2、#108 P1、#109 P1/P2）。いずれも検証のうえ採用・修正済み。

### 2026-07-31: Flywayマイグレーション運用ルール（ALTER TABLE時の注意点）

- **種別**: ユーザー指定
- **対象領域・関連ファイル**: backend / `backend/src/main/resources/db/migration/*.sql`（Flywayマイグレーション全般）
- **何が起きたか**: チャージ型カード機能（F-11拡張）のためのマイグレーション（`cards`/`expenses`テーブルへの`ALTER TABLE`）を計画する際、ユーザーから「ALTER TABLEは手動管理にすべきでは」という懸念が出た。過去に、一度適用済みのマイグレーションファイルの内容を後から書き換えたことで、Flywayのchecksum不一致（DB側の記録と手元のファイル内容の食い違い）によるトラブルが発生し、手動対応で解消した経験があるとのこと。
- **対応**: Flywayによる自動適用の仕組み自体は維持する（結合テスト・CIがFlywayの自動適用に依存しているため、手動管理に切り替えると再現性が壊れる）。その上で、トラブルの実体（checksum mismatch）を避けるための運用ルールを徹底することで合意した。同種の原則は他プロジェクトでも通用する一般知識のため`tech-notes` Skill（`references/flyway.md`、このマシン限定・リポジトリ管理外）にも背景・根拠込みで集約しているが、実践に必要なルール自体は本ファイルに完結させる。
- **次回の行動規則**:
  - 開発中（まだPRを出す前＝リモート・他環境に一度も反映していないマイグレーションファイル）は内容を自由に修正してよい。修正するたびに `docker compose down -v && docker compose up -d` でローカルDBを作り直し、Flywayを最初から再適用させる（このプロジェクトはローカルDocker運用のみのため、作り直しコストはゼロに近い）。
  - 一度でもPRを作成しリモート・他環境に共有されたマイグレーションファイルは、内容を二度と編集しない。修正が必要になったら新しいバージョン番号のファイル（例：V6の後はV7）を追加して対応する。
  - `NOT NULL`制約を持つカラムを既存テーブルに追加する際は、必ず`DEFAULT`句を指定し、既存行への値設定漏れ（NOT NULL違反によるマイグレーション失敗）を防ぐ。
  - `ALTER TABLE`を含むマイグレーションを追加するPRでは、同じ変更の中でEntity・Mapper（XMLのResultMap・INSERT/UPDATE文）・DTOも必ず同時に更新し、スキーマとアプリケーションコードの不整合を残さない。
  - **本番運用開始後にマイグレーションが失敗した場合**：Flywayのマイグレーション失敗時の挙動（`flyway_schema_history`への記録有無、`flyway repair`の効果範囲）はDBMSやDDLの種類（トランザクション内実行かどうか）によって異なり、思い込みで手動SQL操作をすると二重適用等の二次被害を招く。本番導入前にFlyway公式ドキュメントとPostgreSQLでの実機検証で復旧手順を確立し、ランブック化しておく（未検証の推測で手順を確定させない。この項目自体、過去に技術的に不正確な手順を記載しCodexレビューで2度訂正された経緯があるため、実際にトラブルが発生した際に検証済みの内容で書き直す）。
- **状態**: 有効
- **根拠**: チャージ型カード機能の実装計画時のユーザーとの会話（Flyway運用に関する懸念への回答、2026-07-31）。本番運用時の復旧手順に関する記述はcodex reviewで2度技術的誤りを指摘され、詳細手順の記載を見送る方針に変更（2026-08-02）。
