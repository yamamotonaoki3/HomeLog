# パスワード再設定メールの送信設計（#395）

状態: **GAS方式の設計はユーザー承認済み（2026-10-29）。実装・Google側の初期設定・本番反映は後続Issueで行う。現行アプリの挙動はまだ変更しない。**

## 目的と確認済みの条件

- 家族で使うシェファミのパスワード再設定を、利用者自身で完了できるようにする。
- 独自ドメインは購入せず、現在のアプリURLを維持する。
- Googleの仕組みを使うこと自体は問題なく、Gmail APIより初期設定が簡単な方法を優先する（ユーザー確認済み）。
- メール送信サービスは未実装。現在のAPIはトークンだけを発行するのに送信完了と案内し、画面ではトークンの手入力を求めている。

## 方式比較と提案

| 方式 | 初期設定・管理 | 判断 |
| --- | --- | --- |
| Gmail APIをWorkersから直接呼ぶ | Google CloudのOAuth設定・送信者の認可・アプリ側の資格情報更新処理が必要 | 今回の「設定を簡単にする」という希望から優先しない |
| **GASのMailAppをWorkersから呼ぶ** | Apps Scriptに送信処理を配置し、所有者が初回に権限を許可する。Workers側にGoogleのOAuth更新処理を実装しない | **採用。ユーザー承認済み** |
| 外部のメール配信サービス | APIキー方式で連携可能だが、ドメイン不要での送信条件・送信元の表示・サービス審査を個別に確認する必要がある | 今回はGoogle利用が可能なので優先しない |

個人GoogleアカウントのMailAppは、現時点の公式上限で1日100宛先。上限は送信用アカウント単位で他のスクリプトとも共有され、変更される可能性がある。家族用途の送信量なら候補になるが、到達保証や業務用の配信SLAを提供する設計ではない。

## 初期設定の提案

1. 送信専用のGoogleアカウントを1つ用意する。既存アカウントの利用も可能だが、送信元としてそのアドレスが表示されるため専用を推奨する。アカウントの作成・選択はユーザーが行う。
2. 用意したApps Scriptのコードを貼り付け、初回のみMailAppによる送信権限を許可する。
3. スクリプトプロパティにアプリとの共通鍵と固定のアプリURLを登録する。実値はソース・Issue・PR・チャットへ記載しない。
4. Webアプリを「所有者として実行」で公開し、WorkersからGoogleログインなしで呼び出せるアクセス設定にする。公開URLを知るだけでは送信できないよう、毎回署名を検証する。
5. Workers側のsecretに共通鍵と呼出先を設定する。GASの公開・本番secret設定・実メール送信は、本番反映の指示とユーザーによる初期設定が揃ってから行う。

家族それぞれがGASやGoogle連携を設定する必要はない。受信者のメールサービスもGmailに限定しない。コード更新時のGASの再デプロイ手順も用意する。

## 利用者の操作

1. ログイン画面の「パスワードを忘れた場合」から、登録済みメールアドレスを入力する。
2. メール内のリンクを開いて、新しいパスワードを入力する。トークンを手入力する操作は原則不要とする。
3. 既存の30分の有効期限・一度限りの使用・パスワード更新とリフレッシュトークン失効の同一バッチ処理を維持する。

## アプリとGASの境界

- Workersが登録ユーザーの確認・再設定トークンの発行とハッシュ保存・回数制限を担当する。
- GASはWorkersの署名を検証し、固定した再設定メールだけをMailAppで送信する。任意の件名・本文・送信元を指定できる汎用中継にはしない。
- POST本文に送信先・トークン・時刻・要求ID・署名を含める。署名はHMAC-SHA256とし、署名対象の文字列形式・バージョンを固定する。共通鍵自体を送らない。
- GASは署名・時刻の許容範囲・入力形式を検証してから送信する。固定のアプリURLからリンクを組み立て、要求側のHostや任意URLを採用しない。
- 短時間の同一要求IDの再送を検出し、並行要求をロックして重複送信を抑える。MailAppと保存処理を跨ぐ厳密なexactly-onceは保証しない。確認不能な送信を無制限に自動再試行しない。
- 共通鍵・資格情報・トークン・メール本文・POST本文をログへ出さない。Googleへの送信権限は送信所有者が初回に許可し、Gmailの受信箱を読む権限は要求しない。
- GASは公開HTTPSエンドポイントとなる。署名検証は不正送信を防ぐためのもので、Google側の実行枠消費まで防ぐものではない。公開URLを画面へ埋め込まず、監視・必要時の公開停止手順を用意する。

## 回数制限・送信失敗・表示

- 同一メールアドレス・接続元・アプリ全体に送信申請の回数制限を設ける。複数Workersでも制限が崩れないよう、D1内で原子的に判定する。具体的な閾値と保持期間は実装計画で確定する。
- GASではMailAppの残り枠も確認する。アプリ全体の上限はGoogleの上限より低く設定し、失敗が続いた場合は送信停止・復旧案内に切り替えられるようにする。
- 登録の有無・個別の配信失敗からアカウント存在を区別できない申請応答にする。「メールを送信しました」と断定せず、登録済みの場合に案内する旨と、届かない場合の再申請方法を表示する。
- 全体の送信機能が未設定・停止中の場合は、メールアドレスの有無に依存せず同じ利用不可応答を返す。メール送信が使えないのにトークン入力画面へ誘導しない。
- タイムアウト時はメールが送られている可能性がある。成功を断定せず、同一要求の自動再試行を制限する。期限内に届いた正規のリンクは利用できるようにする。
- 利用者が再申請すると以前のリンクは無効になる方針を維持し、メールには最新の案内を使用する旨を記載する。既存の有効リンクと再送・タイムアウトの競合は回帰テストで確認する。
- ログは失敗の分類と秘密情報を含まない相関IDに絞る。監視は送信枠不足・認可失効・署名不一致・タイムアウトを区別する。

## 再設定リンクと秘密情報

- 提案するリンク形式は `/password-reset#token=<opaque-token>`。フラグメントはHTTPリクエストへ送られないため、URLクエリへの記録を避けられる。
- 画面でトークンを読み取ったらURLから取り除き、確認APIのPOST本文でだけ送る。アナリティクスやエラー報告へ渡さない。ページ再読込時にトークンが失われる場合は、メールのリンクを再度開く案内を出す。
- リンクを開くだけではトークンを消費しない。メールサービスのリンク確認機能で勝手に使用済みにならないよう、新パスワードの確定時だけ消費する。
- DBにはトークンのハッシュだけを保存する。メールとGASへの送信時に生トークンを扱うこと自体は必要であり、送信用Googleアカウント・GAS編集者の権限を限定する。

## 必須の検証

- 期限切れ・再使用・同時確定・再申請後の古いリンク・送信タイムアウト・設定未完了・停止中。
- 不正署名・期限外の送信要求・改ざんされた宛先やトークン・同じ要求の並行処理・送信上限。
- 存在しないメールと登録済みメールの応答・回数制限で存在情報が漏れないこと。
- リンクを開くだけでは消費されず、URL・ログ・エラーに秘密情報を残さないこと。
- 通常のlint/typecheck/test/build/E2Eはローカル専用で実施し、実GASや本番メールを呼ばない。実配信の確認は、本番反映時に承認された宛先だけで行う。
