# 全体共通事項

[← 要件定義書に戻る](../requirements.md)

---

機能横断で決まっている方針をここに集約する。個々の機能定義書で重複して記載しない。

## 1. 世帯グループモデル

- ユーザーは「世帯グループ」を作成・参加できる（[[../構想.md]] 2章）。
- 個人の財政（家計簿）は個人が管理し、世帯全体の合算家計簿は持たない。
- 世帯グループが管理するのは「協力購入・立て替えの精算関係」「在庫・買い物リストの共有」「献立表の共有」。
- シェアハウス等、家族に限らない複数人同居でも利用できることを想定。

## 2. 権限方針

アプリケーション全体の管理権限と世帯グループ内の管理権限は別のロールとして扱う。個人の家計・口座等は世帯内の共有対象ではなく、世帯管理者であっても閲覧できない。

| 機能 | 権限 |
| --- | --- |
| 個人の家計簿（収入・支出） | 本人のみ閲覧・編集可能。他の世帯メンバーは閲覧・編集不可 |
| 固定費・イベント | 登録時に「個人」か「世帯共有」を選択する（`owner_user_id`、[data-model.md](data-model.md)参照）。個人のものは本人のみ閲覧・編集可能、世帯共有のものは世帯メンバー全員が**閲覧**可能。ただし**編集・削除は登録者のみ**（誤操作防止のため、世帯共有でも他メンバーは不可） |
| 口座・残高 | 所有者本人のみ閲覧・編集可能。個人の財政管理情報として扱い、世帯メンバー間でも共有しない |
| 割り勘・精算 | 相手側（受領/請求の対象者）の承認があって初めて「精算済み」になる |
| 在庫管理・買い物リスト | 世帯メンバー全員が自由に編集可能（権限制限なし） |
| 献立表・レシピ | 世帯メンバー全員が自由に編集可能（権限制限なし） |

世帯管理者、アプリ全体の管理者、例外アクセスおよび個人情報のライフサイクル要件は12章を参照。

## 3. マスタデータ方針

- カテゴリーマスタは **機能ごとに独立** させ、共通化しない（家計簿用カテゴリーと在庫管理用カテゴリーは別物）。
- 在庫管理のカテゴリー・店舗マスタは世帯単位で共有し、使用中のものは削除不可（先に付け替えが必要）。
- 家計簿カテゴリー（支出・収入）は世帯単位で、初回アクセス時に冪等シードされる**デフォルトカテゴリー**（編集・削除不可）と、ユーザーが追加する**カスタムカテゴリー**（編集・削除可、使用中は削除不可）で構成される。UI（S-23）はデフォルトカテゴリーに対して編集・削除ボタンを非表示にする（[F03_kakeibo_expense](features/F03_kakeibo_expense.md) 6-2章, [F13_kakeibo_income](features/F13_kakeibo_income.md) 7-2章参照）。

## 4. 通貨単位

- 支出データの通貨単位は日本円固定とする（多通貨対応は行わない）。

## 5. ID・命名規則

- 機能ID: `F-xx`（`docs/details/features/F0x_*.md` に対応）
- 画面ID: `S-xx`
- ダイアログ/モーダル: `D-xx` / `M-xx`

## 6. 機能間データ連携方針（まとめ）

| 連携元 | 連携先 | 連携有無 |
| --- | --- | --- |
| 在庫管理 | 買い物リスト | 密連携（同一データソース、自動追加・自動反映） |
| 買い物リスト | 家計簿 | 連携なし（支出は都度手動登録） |
| 献立表 | 在庫管理 | 連携なし（材料個数の自動消費は行わない） |
| 献立表 | 家計簿 | 連携なし |

## 7. 口座・カードモデル

- 「口座」（銀行口座・PayPay等の電子マネーを含む）を手動登録できる（[F11_kakeibo_account](features/F11_kakeibo_account.md)参照）。
- 「カード」（クレジットカード等）は口座に紐づく子エンティティとして扱う。カード単体では存在せず、必ずいずれかの口座に属する。
- 支出登録時に、どの口座・カードから出費したかを選択できる（`expenses.account_id`）。
- 外部API（銀行・カード会社・Money Forward ME・PayPay等）との自動連携は今回のスコープ外とし、手動登録のみを要件化する（今後の検討事項）。

## 8. 世帯合計支出・個人収支の扱い

- 個人の収入・支出データが「本人のみ閲覧・編集可能」という原則（2章）は維持する。
- 世帯で合算・共有したいのは「共同で行った買い物・イベント等の支出を割り勘・精算しやすくすること」「今月の共同支出の内訳を把握すること」であり、**世帯合計の対象は支出・固定費のみ**とする。収入は世帯で合算・共有する対象にせず、純粋に個人管理とする（世帯合計対象フラグを持たない）。
- 世帯全体でどれだけ支出があったかの**合計金額**は世帯メンバー全員が確認できるようにする（[F12_kakeibo_household_summary](features/F12_kakeibo_household_summary.md)参照）。
- 個人的な支出（世帯の共同生活に関係しない私的な支出）は世帯合計から除外したいというニーズがあるため、支出・固定費それぞれに **世帯合計対象フラグ**（`include_in_household_total`）を持たせ、フラグがtrueのものだけを合計対象とする。
- 世帯合計に含める・含めないの判定はユーザーが支出登録時に都度指定する（自動判定ロジックは今回のスコープ外）。
- 割り勘の精算完了時に自動作成される収入・支出（[F04_kakeibo_warikan](features/F04_kakeibo_warikan.md) 8章）は、元の共同支出との二重計上を避けるため **`include_in_household_total = false`** で作成し、世帯合計の対象外とする。
- 世帯合計サマリーで開示するのは合計金額のみであり、「誰が何にいくら使ったか」という個別の内訳は非公開のまま。
- トップ画面（S-04）の「収支」表示は、**ログインユーザー本人の収入合計－支出合計**（世帯合計対象フラグの有無に関わらず本人が登録した全件）で算出する個人単位の値である。他メンバーの収入・支出は前述の権限方針により参照できないため、この「収支」は常に本人個人の収支であり、世帯全体の収支ではない（世帯合計支出とは別の指標。[F13_kakeibo_income](features/F13_kakeibo_income.md)参照）。

## 9. 画面設計の基本方針（登録・編集は各機能画面、確認はトップに集約）

- 「今お金・生活まわりで何が起きているか」を都度画面遷移せずに把握できるよう、確認系の情報（今日の収支・今月の支出・未精算額・在庫不足・買い物リスト件数・イベント別支出等）は**トップ画面（S-04：生活ダッシュボード）に集約**する。
- 登録・編集操作は、各機能の専用画面・モーダル（S-06支出登録、S-18イベント登録等）で行う。
- 独立した「確認専用画面」は極力作らず、既存画面のサマリーカードやパネルとして表示する（例：世帯合計支出・イベント別支出サマリーはS-04に統合し、単独画面は持たない）。
- 密連携する機能（在庫管理と買い物リスト等）は、可能な限り同一画面内で同時に確認できるレイアウトにする。

## 10. APIエラーレスポンス方針

- **他人が所有するリソース（例：他人の支出ID、他世帯の在庫ID等）を指定した場合、403 Forbiddenではなく404 Not Foundを返す。**
- 理由：403を返すと「そのIDのリソースは存在するが権限がない」ことを外部に伝えてしまい、IDを総当たりすることで他人のデータの存在・件数・採番規則を推測されてしまう（IDOR/列挙攻撃）。404で統一することで「存在しない」のか「権限がない」のかを区別できなくし、こうした推測を防ぐ。
- 本人の認証自体が失敗している場合（トークンなし・無効・期限切れ）は401 Unauthorizedを返す。
- 入力値のバリデーションエラーは400 Bad Requestを返す。
- 詳細なAPIエンドポイント仕様は[api-design.md](api-design.md)を参照。

## 12. 個人情報保護・管理者権限・例外アクセス

### 12.1 基準と適用範囲

- 個人情報の取扱いは、個人情報保護委員会「個人情報の保護に関する法律についてのガイドライン（通則編）」およびJIS Q 15001:2023を設計の土台とする。
- Webアプリのセキュリティ実装・検証はOWASP ASVS 5.0.0 Level 2を目標とし、認証・認可、入力検証、通信・保存データ保護、ログ、運用等の適用要件を実装時に確認する。
- 将来ネイティブモバイルアプリを提供する場合は、OWASP MASVS v2.1.0（2026-09-26確認）のコントロール群を対象アプリと脅威に応じて選定する。MASVS v2系はコントロール群を定義し、旧来のL1/L2をそのまま各コントロールの達成レベルとして扱わない。
- 今回はユーザーが手入力する家計・世帯・在庫・レシピ等を扱う。銀行・カード会社等の外部APIから個人データを取り込む機能、決済機能、実カード番号/CVV等の登録・保存は対象外とする。口座名・カード名・残高等も個人の財政情報として保護する。
- レベル2の選択は今回合意した機能範囲に対するセキュリティ目標であり、手入力データが低感度であることを意味しない。外部連携、決済、要配慮情報等を追加する場合はリスク評価と目標の見直しを行う。
- ここに記載するのは設計目標であり、法令遵守やJIS認証を保証するものではない。実運用・一般公開前に、実際のデータ処理、事業者体制、委託先、法的義務を別途確認する。

### 12.2 データの取扱い原則

- データを少なく集め、利用目的を定め、目的に必要な範囲でのみ利用する。本人に関する情報の利用目的、問い合わせ・開示等の窓口、保存期間・削除方針を、公開前にプライバシーに関する案内へ反映する。
- アカウント識別情報（メールアドレス、表示名）、認証情報、本人のみの家計・口座情報、世帯内で共有する記録、運用・セキュリティログを区別し、それぞれの閲覧主体、利用目的、保持・削除方針を設計・実装時に対応付ける。
- パスワードは強固な一方向ハッシュで保存する。ログインやパスワード再設定で原文が必要なメールアドレスは、単純なハッシュ化を要件にしない。認証・通知に必要なアクセスを限定し、通信・保存時の保護方法と鍵管理は実装設計で定める。
- アクセス制御は画面上の表示/非表示に依存せず、API等のサーバー側で利用者・ロール・世帯・対象レコード単位に検証する。監査ログには認証情報や家計の本文等、アクセスに不要な機微情報を記録しない。
- 本人からの情報開示・訂正・利用停止等の請求、漏えい等事案の検知・対応・通知については、対象範囲と運用手順を公開・運用前に定める。

### 12.3 世帯管理者

- 世帯作成者を最初の世帯管理者とする。世帯管理者は複数人設定でき、既存の世帯管理者は信頼する世帯メンバーに管理者権限を付与・解除できる。
- 世帯管理者は世帯名、招待・メンバー管理等の世帯運営を担う。管理者であることを理由に、他メンバーの個人家計、収入・支出の個別明細、口座・カード名、残高等へアクセスしてはならない。世帯共有として明示されたデータと集計値のみ、既定の共有権限に従って利用できる。
- 退会する管理者は、他の管理者がいる場合はその管理者体制を維持したうえで退出できる。最後の管理者は退出・アカウント削除の前に後任を指定する。後任不在時の世帯解散・運営継続の扱いは実装前に確定する。
- 管理者権限の付与・解除は本人確認を伴う操作として扱い、誰がいつ誰の権限を変更したか記録する。唯一の世帯管理者を解除・降格する操作は拒否し、後任管理者への引継ぎと同一操作で行う。招待・削除の詳細条件、管理者によるメンバー削除の可否と異議申立て手順は運用設計で確定する。

### 12.4 アプリ全体の管理者と例外アクセス

- アプリ全体の管理者ロールは世帯管理者ロールと分離し、複数人を許可する。既存のアプリ全体管理者が信頼する利用者を管理者に追加・解除できる。唯一のアプリ全体管理者を解除する操作は拒否し、後任への引継ぎと同一操作で行う。初期管理者の設定・復旧手順は一般公開前に定める。
- アプリ全体の管理者は、サービス運用・設定・障害対応に必要な管理機能を持つが、利用者の個人家計、口座・残高、レシピ等の個人コンテンツを通常業務で閲覧できない。管理者という肩書だけでデータ閲覧権限を付与しない。
- 障害・セキュリティ対応等で個人データへのアクセスが不可避な場合に限り、通常ロールとは別の「例外アクセス」を用いる。初期状態は拒否とし、アクセス理由、対象利用者/データ、許可する操作、開始・失効時刻を限定し、期限到来時に自動失効させる。
- 例外アクセスの申請者・承認者・実行者、対象、理由、開始/終了時刻、実行操作を監査可能な形で記録する。申請者本人による自己承認を認めない。二者承認の適用条件、緊急時の事後承認、監査ログの保持期間・閲覧権限は運用要件として別途確定する。
- 例外アクセスを認めても、パスワード、認証トークン、完全な決済カード情報など運用上閲覧不要な秘密は開示しない。個人データへのアクセス制御はサーバー側で強制する。

### 12.5 アカウント変更・退会・データ削除

- メールアドレス変更、パスワード変更、アカウント削除等の重要操作では再認証を求める。メールアドレス変更では、新しいアドレスの所有確認が完了するまで変更を確定しない。変更後は必要に応じて既存セッションを失効させる。
- アカウント削除は、本人の明示的な確認と再認証を必須とし、申請から30日間の取消可能期間を設ける。期間中はログイン等を停止し、本人による取消手順を提供する。期間経過後に削除処理を行う。
- 削除申請前に、未精算の割り勘・固定費負担は精算または他の世帯メンバーへ引き継ぐ。有効な世帯共有固定費も後任に引き継ぎ、個人口座/カードへの参照を解除するか、今後の自動計上を停止して削除する。その後本人は所属世帯から退出する。本人が最後の世帯管理者である場合は後任を指定する。世帯を離れた後の個人データ・共有データの扱いは以下の方針に従う。
- 未精算の割り勘・固定費負担が残る場合の記録と相手側への表示は削除完了前に扱いを確定する。本人の識別情報を消した後も必要な債務記録を保持できるようにし、未決条件が残る間は削除を完了扱いにしない。
- 削除完了時、認証情報、メールアドレス、表示名等のアカウント識別情報と本人専用の個人データは削除する。法令上または紛争対応上の保持根拠があるデータは、対象・根拠・期間・アクセス制限を明確にしたうえで必要最小限に限定する。
- 世帯に残す必要がある共有記録は、目的に必要な範囲に限って保持し、退会者を識別するプロフィールとの紐付けを解除して表示名を「退会したユーザー」とする。これは識別可能性を下げる要件であり、法令上の「匿名加工情報」該当性を意味しない。
- バックアップ、監査記録、法的保持の例外における完全削除までの期間、削除証跡、共有データの具体的な範囲は運用設計で確定し、利用者へ説明する。

### 12.6 未決事項

- アカウント削除の取消期間終了から削除処理の完了までの上限、バックアップからの消去時期、会計・監査目的等による保持期間と法的根拠。
- 共有記録として残すデータの具体的な項目、個人データ削除後に残す最小フィールド、退会者表示の適用範囲。
- 退会時に未精算の割り勘・固定費負担が残る場合の解決手順と、削除処理を保留/完了できる条件。
- 例外アクセスの承認人数/二者承認の必須条件、緊急時の事後承認期限、監査ログの保持期間と定期レビュー方法。
